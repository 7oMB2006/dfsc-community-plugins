# 取回项目记忆

这个插件把记忆存在本地，但**没有任何东西会自动注入**：DFSC 的插件拿不到会话开始事件，
也没有钩子。想让「越用越懂这个项目」成立，取回这一步必须由你主动做。

## 什么时候必须取回

以下任一情况出现，先调用 `memory-hub` 的 `recall`，再动手：

1. **会话开头、第一次接触这个仓库**——用一句概括当前任务去查，确认有没有既定约定。
2. **用户提到过去**——「上次怎么弄的」「不是说过别用 X 吗」「我们之前定的方案」。
3. **你要选实现路线**——建库、选测试框架、定目录结构、改构建脚本之前。
4. **你要推翻一个已有的做法**——先查为什么当初那么做，再决定要不要推翻。
5. **踩坑现场**——报错看起来眼熟，先查有没有记录过的解法。

不需要取回的：纯闲聊、只读解释代码、用户明确说「别管以前的」。

## 怎么调用

```
recall(query: "<关键词或一句话>", project: "<当前工作区绝对路径>")
```

- **`project` 一定要传。** MCP 进程的工作目录是插件安装目录，不是你的项目；
  不传就只能从最近会话推断，多开会话时很容易落到别人的库。
- `query` 写你要找的东西，别写「记忆」：写「构建流程」「测试怎么跑」「为什么不用 webpack」。
- 想只看某一类用 `type`（fact/decision/lesson/preference/pitfall），想按主题筛用 `tags`。
- 查历史结论（包括已被推翻的）用 `status: "all"`；默认只返回 active。

## 怎么用取回的结果

**把记忆当线索，不当事实。** 记忆可能过期，当前仓库和用户的话永远优先：

- 记忆说「用 pnpm」，但仓库里是 `bun.lockb` → 以仓库为准，并把这条记忆 `invalidate`。
- 记忆说「测试跑 npm test」，但你刚看到 `package.json` 里只有 `node --test` → 同样以现状为准。
- 两条记忆互相矛盾 → 都列出来问用户，别自己挑一条当真。

**引用它。** 当记忆确实改变了你的计划，说出来：「按上次记录的约定，构建走 pnpm workspaces」，
并带上记忆 id（`m_xxxxxxxxxxxx`）。这样用户能纠正，也便于以后失效。

**注意副作用。** `recall` 会为返回的条目累加命中次数——这是记忆强化机制，不是只读查询。
正因为如此，不要用无关的宽泛查询去「试试看」，那会把噪声条目顶上来。

## 需要综合多个片段时

问「这个项目的架构是怎么定的」「已知哪些坑」这类问题，用 `reflect`：

```
reflect(question: "构建与测试流程", project: "<绝对路径>")
```

它会按类型分组返回证据，并单独列出**已被推翻**的旧结论和与之冲突的现行条目。
它只做组装，不生成结论——综合判断是你的工作。

## 取不到东西时

- 空的 `memories` 是正常结果，不是故障。不要因为没查到就假设「这项目没规矩」。
- 想确认库在哪、项目归属对不对，调 `stats`；它会报出解析到的项目 slug、来源
  （arg / env / session / fallback）和实际文件路径。
- 一条都没有的领域，正常开展工作；等工作产生了值得留下的结论，再 `retain`。
