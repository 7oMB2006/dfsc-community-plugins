# 整理项目记忆

写入比取回更容易搞砸：写进去的废话会长期占据召回名额，写错的结论会误导以后的会话。
这个技能是一个收敛流程，不是为了「多记点」。

## 什么时候整理

- 用户说「记一下」「把这次的结论存起来」「以后别再犯这个」。
- 一次任务收尾，且确实产生了**以后还会用到**的结论（新约定、新踩的坑、被推翻的旧做法）。
- 执行 `/memory consolidate`。

不需要整理的时候：一次纯问答、一次没结论的探索、用户没要求且你也说不出「下次谁会用到它」。

## 流程

### 1. 取素材

```
history_digest(session: "<当前会话 id>", maxChars: 12000, project: "<绝对路径>")
```

日常收尾**传 `session`**，只读当前这一次对话。会话 id 就是会话文件名里的 UUID——
不要用「最近修改的那个」代替：别的会话可能刚写过，而当前会话还停在开头。
找不到指定会话时工具会如实报错，不会退回猜一个。

跨多次会话归纳时才显式传 `sessions`（最多 10）；不传 `session` 也不传 `sessions` 时，
退回「最近一个」，那只是兜底，不保证是当前对话。

它给的是所取会话的正文摘录（已脱敏、已跳过工具输出与子代理）。
`truncated: true` 表示还有更多没取——**不要**为了凑满而反复调大 `maxChars`，
一轮 12000 字符足够抓出几条真结论；不够就说明这次会话没有那么多值得记的。

也可以不取素材，直接从当前对话里提炼——你对刚才发生的事比摘录更清楚。

### 2. 提炼，一句一条

一条记忆 = 一个能被独立使用的结论。判断标准：**换一个会话、没有上下文，这句话还有用吗？**

好的：

- 「构建用 pnpm workspaces，`packages/*` 各自独立构建」
- 「Windows 上 `node --test` 跑子进程测试偶发 EBUSY，重跑一次即可」
- 「用户要求所有产出中文、命令行给可直接复制的完整路径」

坏的（不要写）：

- 「我们讨论了构建方案」——过程，不是结论
- 「文件改了三个」——一次性事实，没有复用价值
- 「可能有问题，需要再看看」——没有结论的结论
- 任何密钥、token、个人绝对路径、真实账号——写入时会被脱敏，但别指望它

**一轮最多写 12 条。** 写不出 12 条很正常；硬凑一定会污染库。

### 3. 写之前查重

对每个候选结论先 `recall` 一下（同一个 `project`，query 用它的关键词）：

- 已存在，内容相同 → 不要重复写（`retain` 会自动合并，但先查能省一次写入，也让你看到旧条目）。
- 已存在但**已过期/被推翻** → 先 `retain` 新结论拿到 id，再
  `memory_edit(op: "invalidate", id: <旧>, replacementId: <新>)`。
- 已存在且仍然正确 → 可以用
  `memory_edit(op: "update", id: <旧>, importance: 更高)` 提高它的权重，而不是新增一条重复的。

### 4. 写

```
retain(text: "一句话结论", type: "decision", tags: ["构建"], importance: 0.7, project: "<绝对路径>")
```

类型选对，召回分组才准：

| type | 装什么 | 例子 |
| --- | --- | --- |
| `fact` | 客观事实、环境、技术栈 | 「Node 24，Windows 上 bash 优先」 |
| `decision` | 做过的选择 + 为什么 | 「放弃 SQLite 改用 JSON 单文件，为了零依赖可审计」 |
| `lesson` | 可复用的做法 | 「先写失败测试再实现，能抓住方向错误」 |
| `preference` | 用户的稳定口味 | 「产出全中文，命令要能直接复制」 |
| `pitfall` | 踩过的坑 | 「损坏的状态文件必须在锁内备份，否则两进程互相覆盖」 |

`importance`：0.9 是「弄错了会返工」的约定，0.5 是普通事实，0.2 是偶然有用的边角。
`source` 可填会话 id 或 `consolidate:<日期>`，便于以后追溯。

### 5. 复核

```
stats(project: "<绝对路径>")
```

看三件事：

- `banks.project.active` 是否接近 `caps.project`（600）。接近时先处理过时条目，别让系统自动淘汰。
- `topTags` 是否被单一主题淹没——说明你在同一件事上写了太多相似条目，合并它们。
- `corrupt` 是否出现 true——库文件坏了，告诉用户，不要继续写。

## 处理矛盾

绝不静默取舍。两条记忆说法相反时：

1. 都能查到（`recall(status: "all")`），
2. 在回复里说明「记忆里同时存在 A 和 B」，
3. 按当前仓库与用户最新说法保留一条，另一条 `invalidate` 并记 `replacementId`。

## 用户说「清空记忆」

必须先确认范围（当前项目 / 全局 / 两个都清），再做：

```
memory_purge(scope: "project", confirm: "DELETE", project: "<绝对路径>")
```

它把库文件移到 `.trash-<时间戳>` 而不是删除，用户仍能找回。**不要在用户没明确说清空前主动调用。**
